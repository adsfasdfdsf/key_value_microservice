# Key Value Service

Распределенное хранилище key-value пар. Бэкенд на Go, фронтенд на React.
Можно зарегистрироваться, добавлять пары и смотреть свои значения. У каждого пользователя свой набор ключей.

## 1. Запуск

Нужны Docker и Docker Compose. Из корня проекта:

```bash
docker compose up -d --build
```

После сборки открыть http://localhost:8080. С другого компьютера в сети — `http://IP_КОМПЬЮТЕРА:8080`.
Фронтенд отправляет API-запросы через свой nginx, адрес бэкенда в коде менять не надо.

При старте нужно немного подождать, пока узлы выберут master. В это время запросы могут возвращать 503.

Остановить:

```bash
docker compose down
```

Данные остаются в volumes. `docker compose down -v` удалит их вместе с базами.

Для работы над фронтендом отдельно, при запущенном бэкенде:

```bash
cd frontend
npm ci
npm run dev
```

Открыть http://localhost:5173. Vite проксирует `/api` на `localhost:1128`.
Если нужен другой адрес API, его можно задать через `VITE_API_URL`.

## 2. Архитектура

```text
React -> Auth -> Nginx -> master / replica1 / replica2
```

- **Auth** — регистрация, вход и проверка JWT. Пользователи и токены хранятся в отдельной PostgreSQL.
- **Nginx** — отправляет запросы на доступные storage node. Фоновая проверка убирает из upstream узлы, которые еще не готовы.
- **Master** — принимает записи и передает их репликам по gRPC.
- **Replica** — отвечает на чтение из своей базы. Если на нее пришла запись, пересылает ее master.

У каждой storage node своя PostgreSQL. Названия `master`, `replica1`, `replica2` в compose постоянные, но роль master может перейти к другому узлу без перезапуска.

### Выборы и запись

Всего узлов три. Для записи нужно подтверждение хотя бы двух. Если остался один, записать данные не получится.

При выборах используется ballot: номер раунда и ID узла. Узел сохраняет обещанный ballot в базе и больше не принимает предложения с меньшим номером. Кандидат собирает принятые записи через `Prepare`, для каждой позиции берет запись с наибольшим ballot и подтверждает журнал большинством. После этого становится master.

Сначала операция сохраняется в журнал через `AcceptEntries`. Когда ее подтвердили два узла, `CommitEntries` применяет записи по порядку. Обновление данных и примененной позиции журнала идет в одной транзакции.

Master отправляет heartbeat примерно раз в секунду. Если его нет 5–8 секунд, реплики начинают выборы. При потере большинства или встрече более высокого ballot master отказывается от своей роли.

Чтение идет из локальной базы, поэтому реплика может ненадолго отставать. Если запрос на запись закончился таймаутом, это еще не значит, что запись не прошла: она могла сохраниться на большинстве узлов. Отдельной защиты от повторного выполнения клиентских запросов пока нет.

### Журнал и snapshots

В `operation_log` лежат принятые операции, в `consensus_state` — ballot и примененная позиция. Снимки состояния сохраняются в `snapshots` после первой и затем каждой сотой примененной операции, вместе с SHA-256 для проверки.

При запуске узел восстанавливается из снимка и оставшейся примененной части журнала. Вернувшаяся реплика догоняет master по журналу и до этого не принимает обычный трафик.

Журнал пока не очищается. Передачи больших журналов по частям тоже нет, лимит gRPC-сообщения — 32 МиБ. Добавление новых узлов и шардирование пока не сделаны.

## 3. API

### Auth

Через фронтенд API доступен на порту 8080, напрямую Auth — на `localhost:1128`.

| Метод | Путь | Описание |
|-------|------|----------|
| POST | `/api/v1/signup` | Регистрация |
| POST | `/api/v1/login` | Вход |
| GET | `/api/v1/auth/refreshTokens` | Обновить access и refresh токены |
| GET | `/api/v1/getUserKeys` | Получить свои пары |
| POST, PUT | `/api/v1/addKey` | Добавить или заменить значение |

Для регистрации и входа body:

```json
{
  "email": "user@example.com",
  "password": "password123"
}
```

Пароль при регистрации — от 8 до 72 байт. В ответе приходит `accessToken`, refresh токен сохраняется в HttpOnly cookie.
Для запросов с данными нужен заголовок `Authorization: Bearer <accessToken>`.

Добавить пару через `/api/v1/addKey`:

```json
{
  "key": "name",
  "value": "Alex"
}
```

Пользователя Auth берет из JWT. При успешной записи ответ — `200` и `{"success": true}`.

### Storage node

Внутреннее API доступно через nginx на `localhost:80`.

| Метод | Путь | Описание |
|-------|------|----------|
| POST, PUT | `/api/v1/addValue` | Добавить или заменить значение |
| GET | `/api/v1/value/{key}?user=...` | Получить значение по ключу |
| GET | `/api/v1/values/{user}` | Получить все пары пользователя |

Добавить пару напрямую:

```json
{
  "user": "user@example.com",
  "key": "name",
  "value": "Alex"
}
```

Получить: `GET /api/v1/value/name?user=user@example.com`.
Ответ:

```json
{
  "user": "user@example.com",
  "key": "name",
  "value": "Alex"
}
```

При успешном запросе — `200`, если ключ не найден — `404`. Во время выборов или восстановления может прийти `503`, тогда стоит повторить запрос позже.

У узлов также есть `/health/live`, `/health/ready` и `/api/v1/status`. Последний показывает роль, ballot, адрес лидера и позиции журнала.

Storage API не проверяет JWT, поэтому пользовательские запросы должны идти через Auth. В compose порты 80 и 1128 привязаны к localhost, наружу открыт фронтенд на 8080.

Формат gRPC-сообщений между узлами находится в `storage-node/api/v1/grpc/node.proto`.

## 4. Настройки и старые базы

В compose уже стоят локальные пароли и JWT-секреты для запуска. Для размещения сервиса снаружи нужны свои пароли PostgreSQL, HTTPS и два разных случайных секрета `ACCESS_TOKEN_SECRET` и `REFRESH_TOKEN_SECRET`, каждый минимум 32 байта. Их можно задать в `.env` в корне. После смены секретов придется войти заново.

Для HTTPS поставить `COOKIE_SECURE=true`. Если обращаться к Auth напрямую с другого origin, добавить его в `CORS_ORIGINS` (несколько адресов через запятую).

Схему storage создает init SQL, а сервис `storage_schema` перед запуском узлов применяет ее и к существующим базам. Ключ в `key_values` составной: `(user, key)`.

Если обновлять старую установку:

- Сначала сделать копии баз. Первый переход на журнал запускать со всеми тремя доступными узлами. Старые ключи собираются в начальный снимок; если значения одного ключа у узлов разные, выборы остановятся с ошибкой. Эти расхождения нужно разобрать перед продолжением.
- У Auth раньше volume был подключен к `/data/postgres`, теперь к `/var/lib/postgresql` для PostgreSQL 18. Старые данные могли остаться в анонимном volume. Их нужно выгрузить через `pg_dump` и восстановить в новой базе, а не удалять старые volumes сразу.

## 5. Проверки

Для storage node:

```bash
cd storage-node
go test -race ./...
go vet ./...
```

Тесты с PostgreSQL запускаются с отдельным DSN. Тест создает временную схему и после себя удаляет ее:

```bash
TEST_POSTGRES_DSN='postgres://USER:PASSWORD@HOST:PORT/DB?sslmode=disable' go test -race ./internal/storage/postgres -v
```

Для Auth, из корня проекта:

```bash
cd auth
go test -race ./...
go vet ./...
```

Для фронтенда, тоже из корня:

```bash
cd frontend
npm ci
npm run lint
npm run build
```
