# Распределённое key-value хранилище

React → Auth → Nginx → три storage-node с отдельными PostgreSQL.

## Запуск

Нужны Docker Desktop и Docker Compose. Из корня репозитория:

```bash
docker compose up -d --build
```

Интерфейс: http://localhost:8080. В локальной сети можно открыть `http://IP_КОМПЬЮТЕРА:8080`: API использует тот же адрес, поэтому менять JavaScript и CORS не нужно.

Остановка без удаления данных:

```bash
docker compose down
```

При первом запуске дождитесь выбора лидера. Во время выборов и в коротком окне между отказом узла и его исключением из upstream запрос может временно отвечать HTTP 503. Повторите запрос после восстановления доступности. Не удаляйте Docker volumes, если данные нужно сохранить.

## Разработка фронтенда

При запущенном бэкенде:

```bash
cd frontend
npm ci
npm run dev
```

Vite открывается на http://localhost:5173 и проксирует `/api` в Auth на порт 1128. Для LAN используется адрес, напечатанный Vite в строке Network. `VITE_API_URL` позволяет явно задать другой API.

## Согласование и восстановление

- Все три узла поднимают REST и gRPC; роль лидера меняется без перезапуска.
- Чтение обслуживается локальной базой. Допускается кратковременное отставание реплик: линейризуемое чтение не заявляется.
- Реплика передаёт клиентскую запись лидеру через `SubmitValue`.
- Ballot состоит из номера раунда и постоянного ID узла. Обещание сохраняется в PostgreSQL до ответа на `Prepare`.
- `Prepare` возвращает принятые записи журнала. Кандидат выбирает для каждой позиции значение с наибольшим принятым ballot, повторно подтверждает восстановленный журнал большинством и только затем объявляет себя лидером.
- `AcceptEntries` сохраняет операции в журнал, но не делает их видимыми для чтения. После двух устойчивых подтверждений из трёх `CommitEntries` применяет последовательный префикс журнала и меняет committed index в одной транзакции.
- При потере большинства успешная запись невозможна. Старый лидер, встретив более высокий ballot или потеряв ответы большинства, отказывается от роли.
- Лидер отправляет heartbeat примерно раз в секунду. Реплики запускают выборы после случайного таймаута 5–8 секунд.
- Вернувшаяся реплика получает diff журнала после своего committed index. Незавершённый хвост согласуется с действующим лидером. До догонки она исключается из готовых узлов.
- Контрольные снимки сохраняются в таблице `snapshots` на первой и каждой сотой применённой операции. Снимок содержит JSON состояния и SHA-256. При запуске локальная база восстанавливается из проверенного снимка и оставшегося применённого журнала.
- Журнал пока сохраняется целиком. Снимки не удаляют его: он нужен для восстановления принятых предложений при выборах. Сообщения gRPC ограничены 32 МиБ; автоматическая компактация и передача очень больших журналов по страницам не реализованы.

Если запись завершилась таймаутом или ошибкой после отправки, её итог может быть неизвестен: она могла попасть в большинство и быть восстановлена позднее. Exactly-once для повторов клиентских запросов не заявляется.

## PostgreSQL и обновление схемы

`key_values` содержит `user`, `key`, `value` с составным первичным ключом `(user, key)`.

`consensus_state` хранит обещанный ballot и применённую позицию. `operation_log` хранит принятые операции и флаг применения, `snapshots` — контрольные снимки.

На пустом volume схему создаёт Docker init. Сервис `storage_schema` также идемпотентно применяет расширения схемы к существующим базам до запуска узлов. Сбрасывать базы не требуется.

Для Auth исправлено подключение volume к каталогу данных PostgreSQL 18: `/var/lib/postgresql`. В прежней конфигурации volume был подключён к `/data/postgres`, поэтому реальные данные могли находиться в отдельном анонимном volume. Перед обновлением старой установки экспортируйте Auth-базу через `pg_dump` и восстановите её в правильный volume; автоматически выбирать и удалять анонимные volumes приложение не будет.

При первом переходе со старой версии существующие ключи собираются в начальный снимок из ответов на Prepare. Если базы содержат разные значения одного пользовательского ключа, выборы останавливаются с ошибкой вместо произвольного выбора значения. Перед обновлением сделайте резервные копии баз и запускайте миграцию при доступных трёх узлах. Локальное состояние до первого применения также сохраняется в снимке с индексом 0.

## Доступность

`GET /health/live` — процесс отвечает. `GET /health/ready` — узел готов принимать трафик и база доступна. `GET /api/v1/status` — ID, роль, ballot, адрес лидера и позиции журнала.

Nginx использует отдельный фоновый HTTP probe каждые две секунды, обновляет upstream и исключает неготовые узлы. Проверка может занять больше двух секунд при сетевых таймаутах. Это проверка маршрутизации; выборы и heartbeat выполняют storage-node. Записи Nginx автоматически не повторяет, чтобы не воспроизводить операцию с неизвестным результатом. Таймауты согласованы: gRPC-пересылка записи — 10 секунд, Nginx — 12, клиент Auth — 20.

## API

Auth:

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/signup` | Регистрация: email, password |
| POST | `/api/v1/login` | Вход |
| GET | `/api/v1/auth/refreshTokens` | Ротация токенов через HttpOnly cookie |
| GET | `/api/v1/getUserKeys` | Свои пары ключ-значение |
| POST, PUT | `/api/v1/addKey` | Добавить или заменить key, value |

Для данных требуется `Authorization: Bearer <accessToken>`. Пароль при регистрации — от 8 до 72 байт. Данные пользователя определяются по проверенному JWT.

Внутреннее API узлов через Nginx на порту 80:

| Метод | Путь | Назначение |
|---|---|---|
| POST, PUT | `/api/v1/addValue` | Записать JSON user, key, value |
| GET | `/api/v1/value/{key}?user=...` | Значение по ключу |
| GET | `/api/v1/values/{user}` | Все записи пользователя |

Внутреннее API не проверяет пользовательский JWT. Порт 80 балансировщика и gRPC предназначены для доверенной сети; наружу для пользователей следует предоставлять только интерфейс/Auth. Для публичного развёртывания также нужны TLS, собственные пароли PostgreSQL и секреты JWT.

## Настройки Auth

Compose задаёт локальные секреты для разработки. Перед внешним развёртыванием скопируйте `.env.example` в `.env` и задайте разные случайные `ACCESS_TOKEN_SECRET` и `REFRESH_TOKEN_SECRET`, каждый не короче 32 байт. При смене секретов пользователям потребуется войти заново.

`COOKIE_SECURE=true` используется с HTTPS. `CORS_ORIGINS` — список разрешённых origin через запятую для прямого обращения к Auth. Через встроенный прокси фронтенда CORS не требуется.
